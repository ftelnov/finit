# Product Proposal - Finit

## 1. Обоснование идеи

### Прикладная задача

AI-кодинг-агенты воспринимают свое окружение как чужую зону ответственности. Разработчик настраивает тулчейн, ставит зависимости, конфигурирует MCP-серверы, проверяет версии рантайма, и только *потом* агент может попытаться решить задачу. Когда окружение оказывается неподходящим, агент падает, а разработчик дебажит. Возникает парадокс: человек выполняет сложную системную работу, чтобы агент мог сделать простую кодерскую.

Корневая причина: у агентов нет модели собственных возможностей. Они не знают, что могут и чего не могут, пока не попробуют и не провалятся. Они не анализируют *почему* провалились и не могут расширить себя для следующей попытки.

Finit переворачивает эту модель. Агент **владеет своим окружением**. Он анализирует каждую задачу относительно текущего инструментария, находит пробелы, приобретает недостающее (с разрешения пользователя) и только затем приступает к исполнению в полностью подготовленной песочнице, где провал означает баг в логике, а не отсутствующий инструмент.

### Почему это важнее, чем "лучшие промпты"

| Подход | Что решает | Чего не решает |
|---|---|---|
| Лучшие промпты / system instructions | Качество генерации кода при настроенном окружении | Агент не может решать задачи, требующие инструментов, которых у него нет |
| Claude Code CLAUDE.md / rules-файлы | Контекст конкретного проекта | Статично: человек пишет и поддерживает вручную |
| Devin / SWE-Agent | Больше автономии при выполнении | Нет самоуправления окружением; нет интроспекции возможностей |
| Генераторы спеков (Specstory и т.д.) | Более четкие требования до написания кода | Только фаза спеки; нет подготовки окружения, нет ревью |
| **Finit (env-aware agent)** | **Агент развивает свой инструментарий под задачу** | См. ограничения ниже |

Ключевое отличие: Finit не просто выполняет задачи, он **выясняет, что ему нужно для их выполнения**, и приобретает это. Со временем окружение агента обогащается, и класс задач, которые он может решать автономно, расширяется.

## 2. Цели и метрики

### Цель проекта

Создать PoC env-aware мультиагентной системы, которая по описанию задачи на естественном языке самостоятельно готовит окружение, автономно выполняет задачу и выдает отревьюенный результат. Целевой показатель: 100% completion rate на задачах, которые решаемы текущим опенсорсным фронтиром в идеальных лабораторных условиях.

### Что значит "100% решаемых задач"

Множество задач определяется так: задачи, которые квалифицированный разработчик мог бы решить, используя ту же опенсорсную фронтир-модель (Qwen-3, DeepSeek-V3 и т.д.) в интерактивной сессии с ручной настройкой окружения. Если человек+модель могут это сделать со стирингом, Finit должен сделать это без стиринга. Задачи за пределами reasoning-способностей модели вне скоупа: это ограничение модели, а не системы.

### Метрики успеха

**Продуктовые метрики:**
- Task completion rate: 100% задач в пределах решаемого фронтира (измеряется на бенчмарк-сьюте из 30+ задач на Go, Python, DevOps).
- Качество: каждый доставленный результат проходит ревью-агента. Не бывает "вот мой лучший результат": либо сделано, либо эскалация с понятным объяснением причин.
- Количество взаимодействий с пользователем: <= 3 на задачу (согласование спеки, согласование окружения, выдача результата). Больше = сбой системы.

**Агентные метрики:**
- Самодостаточность окружения: если задача требует инструмента, которого у агента нет, агент самостоятельно определяет пробел, предлагает решение и закрывает его без дебаг-сессий пользователя.
- Валидность structured output: >= 99% LLM-вызовов возвращают валидный structured output с первой попытки. Это жесткое требование: structured output - механизм, который делает опенсорсные китайские модели пригодными для продакшена. Провалы здесь означают, что нужно чинить схему или промпт, а не менять модель.
- Побег из песочницы: 0.

**Технические метрики:**
- Холодный старт контейнера (gVisor): < 10 секунд.
- Целевой показатель по E2E-латенси отсутствует. Цель - гарантированное качество, не скорость. 30-минутная задача, которая работает, лучше 5-минутной, которая не работает.

## 3. Сценарии использования

### Happy path: "Добавь health check эндпоинт"

1. Пользователь: "Добавь эндпоинт /healthz в Go-сервис, который возвращает 200 OK с аптаймом."
2. Семантический роутер классифицирует: `[go-backend]`. Маршрутизирует к Go-специализированному генератору спеков.
3. Спека сгенерирована: путь эндпоинта, схема ответа, тест-план с конкретными ассертами. Пользователь одобряет.
4. Env-aware агент анализирует: Go 1.22 тулчейн - есть. Chi router (из go.mod) - есть. Новых инструментов не нужно. Поднимает gVisor-песочницу с примонтированным проектом.
5. Агент-разработчик реализует хендлер + тест. Полный YOLO.
6. Ревью-агент: запускает `go test`, проверяет соответствие ответа схеме из спеки, проверяет, что не затронуты посторонние файлы. Доказательство: вывод тестов. Вердикт: PASS.
7. Пользователь получает дифф + отчет ревью.

### Ключевой сценарий: агент обнаруживает и закрывает пробел в возможностях

1. Пользователь: "Добавь Prometheus-метрики в сервис."
2. Спека сгенерирована, одобрена.
3. Env-aware агент анализирует: задача требует Prometheus client library (нет в go.mod) и способ верифицировать вывод метрик-эндпоинта. Сейчас у агента нет инструмента для тестирования метрик.
4. Агент **самостоятельно** оценивает кандидатов:
   - `prometheus/client_golang`: проверяет по политикам (лицензия, поддерживаемость, известные уязвимости, активность репозитория). Результат: Apache-2.0, активно поддерживается, CVE отсутствуют. Решение: ставим.
   - `promtool`: входит в состав `prometheus`, тот же профиль безопасности. Решение: ставим в песочницу.
5. Агент устанавливает зависимости в изолированную песочницу, верифицирует (`promtool --version` успешен), переходит к разработке. **Пользователь не вовлечен** - все установки происходят внутри изолированного контейнера, риск ограничен периметром песочницы.
6. Агент-разработчик реализует метрики. Полный YOLO.
7. Ревью-агент: запускает тесты, использует `promtool` для валидации формата метрик. PASS.

**Почему это важно:** агент не просто обнаружил пробел, а самостоятельно оценил и закрыл его. Без env-awareness агент начал бы писать код, наткнулся на "promtool: command not found" посреди работы и либо спросил пользователя, либо выдал невалидированный результат. С env-awareness, но без автономной установки, агент остановился бы и ждал одобрения на каждый инструмент - что создает тот же стиринг, от которого мы уходим.

**Когда агент все-таки спрашивает пользователя:** если действие выходит за границу песочницы (монтирование хостового сокета Docker, сетевой доступ к внешним API, изменение файлов на хосте). Установка инструмента *внутрь* изолированного контейнера не требует одобрения - это безопасно по конструкции.

### Ключевой сценарий: мультидоменная задача

1. Пользователь: "Докеризуй Go-сервис и добавь CI-воркфлоу для GitVerse."
2. Семантический роутер классифицирует: `[go-backend, devops]`. Маршрутизирует к мультидоменному генератору спеков.
3. Спека включает: Dockerfile, YAML CI-воркфлоу, интеграционный тест, который собирает образ.
4. Env-aware агент: нужен Docker CLI в песочнице, нужно знание схемы GitVerse CI. Проверяет: Docker CLI доступен через монтирование хостового сокета (запрашивает разрешение). GitVerse CI - проверяет наличие MCP-сервера или документации. Если MCP-сервер есть, разворачивает. Если нет, фолбечит на получение документации.
5. Агент-разработчик пишет Dockerfile + CI-конфиг.
6. Ревью-агент: собирает Docker-образ в песочнице, валидирует CI YAML по схеме. На основе доказательств.

### Edge case: несогласие по спеке

1. Спека неверно интерпретирует намерение пользователя.
2. Пользователь отклоняет: "Нет, я имел в виду WebSocket, а не HTTP polling."
3. Finit перегенерирует, пользователь одобряет со второго раза.
4. Это считается как 2 из <= 3 допустимых взаимодействий. В рамках бюджета.

### Edge case: провал ревью с протоколом доказательств

1. Агент-разработчик выдает код, который компилируется, но содержит data race.
2. Ревью-агент запускает тесты с флагом `-race`, захватывает вывод: `WARNING: DATA RACE`. Это **эмпирическое доказательство** из исполнения.
3. Ревью-агент формирует структурированный отчет о провале с приложенным доказательством.
4. Агент-разработчик получает отчет и фиксит рейс.
5. Если после N итераций все еще не проходит, эскалация пользователю включает: спеку, код, вывод тестов и оценку ревью-агента. Пользователь получает достаточно контекста, чтобы понять, что произошло.

**Протокол ревью-агента:** каждый фаундинг должен быть подкреплен (а) формальным рассуждением, прослеживаемым по коду ("функция X вызывается без удержания лока Y, что видно на строке Z"), либо (б) эмпирическим доказательством (вывод теста, фрагмент лога, отчет статического анализа). Необоснованные "мне кажется, тут может быть ошибка" не являются валидными фаундингами.

### Edge case: задача за пределами возможностей модели

1. Пользователь запрашивает сложную задачу по распределенным системам, которая требует reasoning за пределами способностей модели.
2. Агент-разработчик пытается, ревью-агент отклоняет с доказательствами (тесты падают, логика несостоятельна).
3. После N итераций система эскалирует: "Задача превышает возможности текущей модели. Вот что было предпринято и почему не получилось: [структурированный отчет]."
4. Никаких притворств, что получилось. Никаких частичных результатов, представленных как законченные.

## 4. Ограничения

### Технические ограничения

| Метрика | Целевой показатель | Обоснование |
|---|---|---|
| Генерация спеки (p95) | < 30с | Спека короткая; один LLM-вызов со structured output |
| Анализ окружения (p95) | < 2 мин | Может требовать сканирования файлов проекта + reasoning об инструментарии |
| Холодный старт контейнера (gVisor) | < 10с | Не должен доминировать в латенси задачи |
| Валидность structured output | >= 99% | Ключевой механизм качества; если ниже - баг в схеме/промпте |
| E2E латенси | Без целевого показателя | Качество важнее скорости. Измеряем, но не оптимизируем. |

### Операционные ограничения

- **Модели:** только опенсорсный фронтир (Qwen-3, DeepSeek-V3 или эквивалент). Никакого фолбека на проприетарные модели. Это жесткое ограничение: система должна работать с тем, что доступно on-prem. Structured output-схемы - основной механизм для выжимания качества: они устраняют неоднозначность формата, сужают пространство выходов и делают валидацию механической.
- **Вычислительные ресурсы:** одна машина, 32GB+ RAM, GPU для локального инференса (vLLM/Ollama). Облачный API как опция, но не требование.
- **Безопасность:** gVisor-песочница для всего исполнения агентов. Deny-by-default для разрешений. Пользователь - единственный авторитет.

## 5. Архитектурный набросок

### Модули

```
User Interface (CLI)
        |
        v
  Semantic Router         <-- LLM, классификация доменов задачи
        |                     (может маршрутизировать в несколько: [go, devops, ...])
        v
  Task Manager            <-- создание/трекинг задач, хранение спеков
        |
        v
  Spec Generator          <-- domain-aware, structured output
        |                     генерирует тестируемые критерии приемки
        v
  Env-Aware Agent         <-- КЛЮЧЕВАЯ ИННОВАЦИЯ
        |                     интроспекция возможностей vs. потребности задачи
        |                     приобретение инструментов, MCP-серверов, зависимостей
        |                     подготовка gVisor-песочницы
        v
  Development Agent       <-- исполнение в песочнице, Polished YOLO
        |
        v
  Review Agent            <-- изолированная песочница, evidence-based ревью
        |                     формальное рассуждение ИЛИ исполнение+логи
        v
  Result Presenter        <-- дифф, результаты тестов, отчет ревью
```

### Env-Aware Agent: детальный разбор

Env-aware агент - это не просто установщик зависимостей. Он поддерживает **модель возможностей** (capability model): структурированное представление того, какие инструменты, рантаймы, MCP-серверы и навыки доступны в текущем окружении. Для каждой задачи:

1. **Анализ:** разбор спеки и определение необходимых возможностей (например, "Go 1.22", "Docker CLI", "promtool", "GitVerse CI MCP server").
2. **Дифф:** сравнение необходимых возможностей с текущей моделью возможностей.
3. **Планирование:** для каждого пробела определяется стратегия приобретения:
   - Установить пакет в песочнице (например, `apt install promtool`) - автономно
   - Добавить проектную зависимость (например, `go get prometheus/client_golang`) - автономно
   - Развернуть MCP-сервер (например, GitVerse CI tools) - автономно
   - Запросить ресурс за пределами песочницы (например, доступ к Docker-сокету) - требует одобрения пользователя
4. **Валидация по политикам:** для каждого инструмента/зависимости агент проверяет: лицензия, известные CVE, активность поддержки, совместимость. Инструмент, не прошедший политику, отклоняется или эскалируется пользователю.
5. **Исполнение:** установка и конфигурация внутри песочницы - автономно. Действия за периметром - только с одобрения пользователя.
6. **Верификация:** подтверждение, что каждая возможность функциональна (например, `promtool --version` успешно).
7. **Обновление:** персистенция модели возможностей для будущих задач.

Со временем модель возможностей растет. Задачи, которые при первой встрече требовали настройки, при повторной встрече обрабатываются мгновенно.

### Интеграции

- **LLM-провайдеры:** OpenAI-совместимый API (vLLM, Ollama, облачные API). Все вызовы используют structured output (JSON schema / tool use). Промпты оптимизированы под конкретные семейства моделей - не "model-agnostic" дженерики, а заточенные промпты под Qwen/DeepSeek/и т.д.
- **Песочница:** gVisor (runsc). Один уровень изоляции для PoC.
- **MCP-серверы:** динамически разворачиваются env-aware агентом внутри песочницы. Агент обнаруживает доступные MCP-серверы, оценивает по политикам и разворачивает автономно. Доступ к ресурсам за пределами песочницы (хостовые сокеты, внешние API) требует одобрения пользователя.
- **Семантический роутер:** LLM-классификатор, который маппит описание задачи на один или несколько доменов. Не keyword matching, а полноценное семантическое понимание. Задача "Докеризуй Go-сервис и добавь CI" маршрутизируется в `[go-backend, devops]`, а не просто в "devops."

### Ключевые проектные решения

1. **Env-aware до code-aware.** Первая задача агента - подготовить окружение, а не писать код. Это устраняет весь класс провалов "агент упал, потому что нет инструмента X."
2. **Polished YOLO.** Окружение тщательно подготовлено, разрешения выданы заранее, спека одобрена. Затем исполнение полностью автономное. Не сырой YOLO (авось заработает). Polished YOLO (обеспечили, что может заработать).
3. **Evidence-based ревью.** Ревью-агент обязан доказывать свои фаундинги через формальное рассуждение по коду или доказательства из исполнения. Это предотвращает ложные отрицания (отклонение хорошего кода на вайбах), которые заперли бы агента-разработчика в бессмысленных циклах исправлений.
4. **Structured output как уравнитель качества.** Каждый LLM-вызов имеет JSON-схему. Это не опционально и не "nice to have": это ключевой механизм, делающий опенсорсные китайские модели пригодными для продакшен-использования. Он обнуляет вероятность мусора на уровне формата и вынуждает модель рассуждать внутри заданной структуры.
5. **Никакого фолбека на другие модели.** Система спроектирована для работы с настроенной моделью. Если задача слишком сложна, система честно эскалирует, а не тихо переключается на более дорогую модель. Это делает систему предсказуемой и прозрачной по стоимости.

## 6. Data Flow

```
Ввод пользователя (текст)
    |
    | [LLM - семантический роутер, классификация доменов]
    v
Запись задачи (структурированная, мультидоменная)
    |
    | [LLM - генерация спеки, structured output, domain-aware]
    v
Спецификация (JSON, с тестируемыми критериями приемки)
    |
    | [Чекпоинт пользователя: одобрение спеки]
    v
Анализ возможностей
    |
    | [LLM - env-aware агент, анализ спеки vs. модель возможностей]
    | [Система - дифф возможностей, планирование приобретения]
    v
План окружения (структурированный: что установить/развернуть/запросить)
    |
    | [Система - валидация по политикам (лицензия, CVE, поддерживаемость)]
    | [Система - автономная установка внутри песочницы]
    | [Чекпоинт пользователя: ТОЛЬКО если нужны ресурсы за периметром песочницы]
    v
Готовая песочница (gVisor, все инструменты верифицированы)
    |
    | [LLM - агент-разработчик, итеративное написание кода]
    | [Система - исполнение кода, запуск тестов в песочнице]
    v
Артефакты (код, тесты, конфиги)
    |
    | [LLM - ревью-агент, evidence-based оценка]
    | [Система - исполнение тестов, статический анализ, захват логов]
    v
Отчет ревью (структурированный, с доказательствами)
    |
    | [Система - форматирование, упаковка]
    v
Вывод пользователю (дифф + отчет ревью)
```

### Делегация LLM vs. детерминистика

| Фаза | LLM/Агент | Детерминистика/Система |
|---|---|---|
| Прием задачи | Семантическая маршрутизация (классификация доменов) | Валидация входных данных, создание записи задачи |
| Генерация спеки | Составление спеки по задаче + контексту проекта + доменным знаниям | Валидация по схеме, формализация критериев приемки |
| Анализ окружения | Reasoning о необходимых возможностях для задачи | Дифф модели возможностей, генерация плана приобретения |
| Подготовка окружения | Выбор стратегии приобретения для каждого пробела | Установка инструментов, разворачивание MCP, enforcement разрешений, верификация |
| Разработка | Написание кода, тестов, итерация по фидбеку ревью | Исполнение кода, запуск тестов, операции с файловой системой |
| Ревью | Рассуждение по коду, поведенческая оценка, проверка соответствия спеке | Исполнение тестов, статический анализ, захват логов, форматирование отчета |
| Эскалация | Объяснение, почему задача не может быть выполнена | Структурирование отчета о провале, упаковка артефактов |
