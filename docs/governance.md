## 2. Политика логирования и работы с данными

### Ретенция логов

- Все действия агентов (вызовы инструментов, LLM-запросы/ответы, жизненный цикл контейнеров, изменения модели возможностей) логируются локально.
- Логи хранятся только на машине пользователя. Никакой внешней отправки в PoC.
- Ретенция: 30 дней по умолчанию, настраивается.

### Персональные данные

- Finit не собирает и не обрабатывает персональные данные за пределами того, что содержится в кодовой базе пользователя.
- On-prem инференс (дефолтный режим) гарантирует, что данные не покидают машину.
- Если используется облачный инференс, пользователь предупреждается при настройке, что содержимое кодовой базы будет передано провайдеру.

### Прозрачность LLM-вызовов

- Каждый LLM-вызов логируется с: таймстемпом, ID модели, фазой (routing/spec/env/dev/review), количеством токенов, используемой structured output-схемой, результатом валидации ответа.
- Полное логирование payload: выключено по умолчанию (избегаем хранения кода в логах в открытом виде). Включается через конфиг для отладки.

### Аудит модели возможностей

- Каждое изменение модели возможностей (добавление инструмента, разворачивание MCP-сервера, выдача разрешения) логируется с: таймстемпом, задачей-триггером, статусом одобрения пользователем.
- Сама модель возможностей - человекочитаемый файл, который можно инспектировать и редактировать.

## 3. Защита от injection и подтверждение действий

### Защита от prompt injection

1. **Structured output как ограничитель**: все LLM-вызовы используют JSON-схемы. Модель заполняет поля, а не фристайлит. Это основная защита от injection, вызывающего off-task поведение с опенсорсными моделями.
2. **Разделение данных и инструкций**: файлы проекта и пользовательский ввод передаются как параметры данных в структурированном вводе, никогда не интерполируются в системные/инструкционные промпты.
3. **Спека как якорь доверия**: одобренная пользователем спека - единственный источник истины о том, что агент должен делать. Ни файл в кодовой базе, ни ответ MCP-сервера, ни вывод инструмента не могут ее переопределить.
4. **Изоляция ревью-агента**: ревью-агент имеет нулевой доступ к промптам, reasoning-у или внутреннему состоянию агента-разработчика. Он видит только: спеку и артефакты. Это предотвращает ситуацию, когда injection, скомпрометировавший агента-разработчика, также компрометирует ревью.

### Модель подтверждения действий

**Deny-by-default.** Пользователь - единственный авторитет. Разрешения запрашиваются заранее (на этапе подготовки окружения), чтобы избежать прерываний в процессе работы.

| Действие | Подтверждение |
|---|---|
| Чтение файлов внутри песочницы | Не требуется (auto-allowed) |
| Запуск тестов / статического анализа внутри песочницы | Не требуется (auto-allowed) |
| Установка инструментов/пакетов в песочницу | Не требуется - песочница изолирована. Агент проверяет по политикам (лицензия, CVE, поддерживаемость) и ставит автономно. |
| Добавление проектных зависимостей | Не требуется - аналогично, проверка по политикам, установка в песочнице |
| Разворачивание MCP-сервера внутри песочницы | Не требуется - изолировано, агент разворачивает автономно |
| Сетевой egress к конкретным доменам | Одобряется как часть плана окружения (заранее) |
| Монтирование дополнительных хостовых директорий | Per-action подтверждение |
| Пуш кода в удаленный репозиторий | Всегда требует подтверждения |
| Модификация файлов за пределами проектной директории | Всегда требует подтверждения |

Цель: **все разрешения решены до начала разработки.** Агент-разработчик работает в Polished YOLO: ему не нужно останавливаться и спрашивать.

### Модель безопасности песочницы

```
Хостовая система
  |
  |-- [Граница разрешений - управляется пользователем]
  |
  +-- gVisor-контейнер (runsc)
        |-- Примонтировано: директория проекта (read-write)
        |-- Примонтировано: тулчейн + приобретенные инструменты (read-only)
        |-- Сеть: запрещена по умолчанию, allowlist per-task
        |-- Capabilities: минимальные (no CAP_SYS_ADMIN, no CAP_NET_RAW, ...)
        |-- Ресурсы: cgroup-limited (CPU, memory, disk, PIDs)
        |-- Время жизни: привязано к задаче, уничтожается по завершении
        |-- Модель возможностей: персистится между задачами (на хосте, не в контейнере)
```
