# Finit

### From intent to finished.

---

Finit bridges the gap between human intent and autonomous execution in software development. You describe what you want — the system handles environment, tooling, coordination, review — and only asks when it genuinely cannot proceed.

Today's AI coding agents treat their environment as someone else's problem. They break when a tool is missing, a runtime is wrong, or a dependency isn't configured. The developer becomes the agent's babysitter — debugging environments so the agent can do simple work.

Finit inverts this. Agents own their environment. They analyze tasks before attempting them, identify capability gaps, acquire what's missing, coordinate with each other through shared knowledge, and deliver reviewed results. The developer steers with intent, not with manual labor.

### Проблема

Современные кодинг-агенты ломаются молча или громко, когда сталкиваются с пробелами в окружении: отсутствует CLI-инструмент, неправильная версия рантайма, недоступный API, нет нужного MCP-сервера. Агент не может это исправить: он либо спрашивает пользователя (ломая поток), либо повторяет тот же нерабочий подход в цикле (тратя токены и время).

**Глубинная проблема:** агенты воспринимают свое окружение как данность. Они не анализируют *почему* не могут решить задачу и не могут расширить свои возможности. Каждый новый класс задач требует ручной настройки от человека.

**Для кого:** разработчики, которые хотят делегировать целые задачи (не только генерацию кода) агенту, но сегодня вынуждены предварительно все настраивать и сидеть у терминала, чтобы помогать процессу.

### Ключевая инновация: Env-Aware Agent

Агент Finit **управляет и развивает собственный инструментарий**. Перед написанием кода он анализирует задачу относительно текущих возможностей:

- Определяет, какие инструменты, рантаймы, зависимости и MCP-серверы нужны
- Выясняет, что уже есть, а чего не хватает
- Приобретает недостающие возможности (устанавливает инструменты, разворачивает MCP-серверы, настраивает доступы) с разрешения пользователя
- Учится на задачах, которые не мог решить качественно, наращивая окружение со временем

Это не "установить зависимость". Это агент, который рассуждает о собственном пробеле в компетенциях и закрывает его до попытки решения задачи.

### Что делает PoC

1. **Прием задачи** - пользователь описывает задачу; семантический роутер классифицирует и маршрутизирует ее (задача может охватывать несколько доменов, например Go backend + DevOps).
2. **Спецификация** - генерирует структурированную спеку с тестируемыми критериями приемки; пользователь согласовывает.
3. **Подготовка окружения** - env-aware агент анализирует пререквизиты, оценивает инструменты по политикам (лицензия, CVE, поддерживаемость) и автономно устанавливает их внутри изолированной песочницы. Пользователь вовлекается только если нужен доступ к ресурсам за периметром (хостовый сокет, внешний API).
4. **Автономная разработка** - выполнение в gVisor-песочнице. Полный YOLO, без взаимодействия в процессе.
5. **Изолированное ревью** - отдельный агент-ревьюер проверяет результат по спеке. На основе доказательств: формальное рассуждение по коду или исполнение + анализ логов. Не наказывает за неподтвержденные гипотезы.
6. **Выдача результата** - дифф, результаты тестов, отчет ревью.

### Что PoC НЕ делает (Out of Scope)

- **Мультитенантный или облачный деплой** - только один пользователь, локально/self-hosted.
- **Долгосрочное управление проектом** - нет бэклога, нет кросс-задачных зависимостей.
- **Не-software-engineering задачи** - только классический SE (код, тесты, конфиги).
- **GUI** - CLI/API-first; интерфейс после PoC.
